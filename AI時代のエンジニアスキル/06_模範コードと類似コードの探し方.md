# 06. 模範コードの学び方と、類似コードの探し方

[← 目次に戻る](README.md)

## Part 1：学習に使える模範となるWebアプリ

初学者のうちは、完成された模範コードを眺めて「Webアプリがどう作られているか」を知ることが大事。AIが生成したコードの無駄を見分ける目も養える。

### おすすめの3つ（2026年10月時点で存在・状況を確認済み）

#### 1. RealWorld（Conduit）：比較しながら学ぶなら
- **リンク**：https://github.com/gothinkster/realworld
- **中身**：Medium のようなブログサービス「Conduit」を、同じAPI仕様と同じ見た目で、さまざまなフロントエンド・バックエンドで作った実装集（100以上）
- **向いている理由**：ログイン、記事の投稿・編集、コメント、フォロー、いいね、ページネーションなど、実際のアプリに必要な機能が揃っていて、規模は小さめ
- **学び方**：同じ機能を React と Vue、Django と Express などで見比べる
- **注意**：コミュニティ実装なので品質・更新状況にばらつきがある。スター数が多く、最近も更新されている実装を選ぶ

#### 2. Next.js 公式チュートリアルのダッシュボード：JavaScript/TypeScript なら
- **リンク**：https://github.com/vercel/next-learn（`dashboard/` フォルダ）
- **チュートリアル**：https://nextjs.org/learn/dashboard-app/getting-started
- **中身**：請求書管理ダッシュボード（ログイン、一覧、検索、CRUD、DB接続）
- **向いている理由**：Vercel 公式教材。必要なものだけが書かれ、余計な抽象化がない

#### 3. Fizzy（37signals）：本物の商用プロダクトを見たいなら
- **リンク**：https://github.com/basecamp/fizzy
- **中身**：37signals のかんばん型タスク管理ツール。2025年11月に実運用中の商用コードが公開された
- **向いている理由**：Rails の生みの親 DHH の会社のコードで、**簡潔に書く文化**がよく表れている。18か月・8,000超のコミット履歴も公開
- **注意**：Ruby on Rails の知識が必要。ライセンスは O'Saasy License（競合SaaSとしての利用に制限あり。読んで学ぶのは問題なし）

### そのほかの定番（未確認だが広く知られているもの）
| 名前 | 技術 | 特徴 |
|---|---|---|
| spring-projects/spring-petclinic | Java / Spring Boot | Spring 公式サンプル。Java 系の模範 |
| inertiajs/pingcrm | PHP / Laravel + Vue | 小さな CRM。Laravel の手本 |
| lobsters/lobsters | Ruby on Rails | 実運用中のニュース共有サイト |
| alan2207/bulletproof-react | React | フォルダ構成や設計の考え方の指針 |

※ Mastodon、Discourse、Cal.com なども有名だが、規模が大きく最初の1本には不向き。

### 選び方
- **JavaScript/TypeScript** → Next.js ダッシュボード → RealWorld の React 版
- **Python** → RealWorld の Django 版か FastAPI 版
- **Rails・本物のプロダクト** → Fizzy
- **Java（業務系）** → spring-petclinic

### 「AIっぽいコード」を見分ける目を養う読み方
1. **ファイル数と行数を数える**：模範コードは同じ機能を驚くほど少ない行数で実現している（`cloc` で比較）
2. **エラー処理の場所を見る**：try-catch を関数ごとに書かず、決まった場所でまとめて処理している
3. **抽象化の数を見る**：インターフェースや基底クラスは、本当に複数の実装がある場合にしか作られていない
4. **null チェックの量を見る**：型や前提条件で保証されている値はチェックしていない
5. **同じ機能をAIに作らせて比べる**：RealWorld の仕様をAIに渡して実装させ、模範と並べて差分を見る（**最も効果的**）

## Part 2：AIが生成したコードを、ネット上の類似コードで確認する方法

### 信頼できる参照先の順番
1. **公式ドキュメント・公式サンプル**：正しい使い方の基準
2. **ライブラリ本体のリポジトリ**（テストや examples）：作者自身の使い方
3. **有名で活発なOSSでの使用例**：現場での書き方
4. **Stack Overflow・技術ブログ**：よくある落とし穴、別の解き方

**ブログや Q&A だけで判断しない。** 古い情報やAIが書いた記事も増えている。

### ① 検索キーワードを取り出す
| 取り出すもの | 例 |
|---|---|
| ライブラリの関数名・クラス名 | `useSearchParams`, `prisma.$transaction`, `revalidatePath` |
| 設定項目・オプション名 | `staleTime`, `onDelete: Cascade` |
| エラーメッセージ（そのまま） | `Hydration failed because ...` |
| import 文 | `from "next/navigation"` |

一般的な変数名（`data`, `handleSubmit`）ではなく、**ライブラリ固有の名前**で検索する。

### ② 公式ドキュメントで「存在」と「使い方」を確認
AIのよくある間違い：**存在しない関数、古いバージョンの書き方、オプション名の間違い**。
- `ライブラリ名 + 関数名 + docs` で検索
- **バージョンを必ず確認**（package.json とドキュメントのバージョンが一致しているか）
- **CHANGELOG・移行ガイド**も見る

### ③ GitHub のコード検索で実例を探す
| 書き方 | 意味 |
|---|---|
| `"prisma.$transaction"` | 完全一致 |
| `language:TypeScript` | 言語で絞り込む |
| `path:app/api` | パスで絞り込む |
| `repo:vercel/next.js` | 特定リポジトリだけ |
| `org:vercel` | 特定組織だけ |
| `/正規表現/` | 正規表現 |

```
"revalidatePath" language:TypeScript path:app
```

そのほかのコード検索：**grep.app**（ログイン不要・高速）、**Sourcegraph**（大規模検索）

**見方**：スター数が多く最近更新されているリポジトリを優先し、**3〜5個の例を比べて共通点を探す**。AIのコードだけ違う書き方なら要確認。

### ④ ライブラリ本体のリポジトリを見る
- `examples/`：公式の使用例
- `test/`, `__tests__/`：エッジケースを含めた正しい振る舞い
- Issues・Discussions：エラーメッセージで検索すると解決策が見つかりやすい

### ⑤ Stack Overflow・技術ブログで落とし穴を探す
- `関数名 + pitfall` / `best practice` / `vs 別の関数名` で検索
- **回答の日付**を確認（古い情報に注意）
- Zenn や Qiita も参考になるが、公式ドキュメントとの照合は必須

### 具体例
```typescript
export async function POST(req: Request) {
  try {
    const body = await req.json();
    const post = await prisma.post.create({ data: body });
    revalidatePath('/posts');
    return Response.json(post);
  } catch (e) {
    console.log(e);
    return Response.json({ error: 'error' });
  }
}
```
模範例と比べて気づくポイント：
- `body` をそのまま `create` に渡している → **入力検証（zod など）がない**
- 認証チェックがない
- エラー時にステータスコードを返していない（200 のまま）
- `console.log(e)` でエラーを握りつぶしている

### AIと検索を組み合わせるコツ
- **根拠を出させる**：「根拠になる公式ドキュメントのURLを示して」→ **自分で開いて確認**（URLも間違えることがある）
- **ドキュメントをAIに渡す**：公式ページを読ませてから「これに沿って書き直して」
- **複数の方法を比較させる**：「ほかの書き方を3つ挙げて、長所と短所を」

### 注意点
- スター数が多い＝正しい、とは限らない
- 見つけたコードを使うときは**ライセンスを確認**（MIT・Apache は比較的自由、GPL や独自ライセンスは条件あり）
- 最終的には**自分で動かして確かめる**

### まとめ
| ステップ | やること | 使うもの |
|---|---|---|
| ① キーワード抽出 | ライブラリ固有の関数名・エラーメッセージを取り出す | コード、AI |
| ② 存在・使い方の確認 | 公式ドキュメントでバージョンも含めて確認 | 公式ドキュメント、CHANGELOG |
| ③ 実例の比較 | 本番プロジェクトでの使い方を3〜5件見比べる | GitHub コード検索、grep.app |
| ④ 作者の使用例 | examples とテストを見る | ライブラリ本体のリポジトリ |
| ⑤ 落とし穴の確認 | よくある問題や非推奨の情報を探す | Stack Overflow、Issues、ブログ |
| ⑥ 動作確認 | 小さなテストで実際に動かす | テストコード |
