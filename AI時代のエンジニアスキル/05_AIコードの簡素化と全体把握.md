# 05. AIで膨らんだコードの簡素化と全体把握

[← 目次に戻る](README.md)

## なぜAIのコードは膨らむのか

- AIはそのとき見えている範囲だけで判断する → **似た処理を別の場所に何度も作る**
- 「念のため」の防御的なコード（不要な null チェック、try-catch）を足しがち
- 将来の拡張を見越した**使われない抽象化**（インターフェース、Factory、設定項目）を作りがち
- 修正を重ねるうちに、**古い実装が消されずに残る**

いきなりリファクタリングすると壊すので、次の順番で進める。

```
① 全体を把握する（地図を作る）
② 安全網を張る（テスト）
③ 無駄を見つける（計測する）
④ 優先順位をつける
⑤ 小さく簡素化する
⑥ 再発を防ぐ
```

---

## ① 全体を把握する：「地図」を作る

**1行ずつ読まず、上から俯瞰する。**

### AIに全体像を説明させる
```
このリポジトリの全体像を把握したいです。コードはまだ変更しないでください。
以下をまとめて docs/architecture-current.md に書いてください。
1. ディレクトリ構成と各ディレクトリの責務
2. 主要な機能の一覧と、処理の入口
3. 主要なデータの流れ
4. 外部サービスとの連携
5. 構成図（Mermaid 形式）
6. 気になった点（責務の重複、構造の不整合、似た処理の散在）
```

### 代表的な処理を1本だけ追いかける
```
「注文を確定する」処理を、ボタンのクリックからDB保存・メール送信まで、
通過する関数を順番にすべて列挙してください。
各ステップで何をしているかを1行で説明し、
不要そうなステップや重複していそうな処理があれば指摘してください。
```
1本通して理解できると、ほかの機能も「同じパターンか、違うのか」で読める。

### ツールで機械的に可視化する（TypeScript/JavaScript の例）
| 目的 | ツール |
|---|---|
| 規模を把握する | `cloc`, `tokei` |
| 依存関係の図・循環参照 | `madge`, `dependency-cruiser` |
| 未使用のファイル・export・パッケージ | `knip` |
| 重複コード | `jscpd` |
| 複雑度の高い関数 | ESLint の `complexity` ルール, SonarQube |

```bash
npx knip
npx jscpd src --min-lines 10
npx madge src --circular --extensions ts,tsx
```
Python なら `vulture`（未使用コード）、`radon`（複雑度）など。

## ② 安全網を張る：テストを先に用意する

テストがない部分は、**今の振る舞いをそのまま記録するテスト**（キャラクタリゼーションテスト）を先に作る。
```
src/services/order/ 配下の現在の振る舞いを固定するテストを書いてください。
「あるべき仕様」ではなく「今の実際の動き」をそのままテストにしてください。
バグっぽい挙動を見つけても修正せず、コメントで報告だけしてください。
```
主要な画面フローを E2E テスト（Playwright など）で数本押さえておくと安心。

## ③ 無駄を見つける：AIコードによくある無駄のパターン

| パターン | 例 | 対処 |
|---|---|---|
| **デッドコード** | 呼ばれていない関数、古い実装 | 削除 |
| **重複** | 日付フォーマット関数が5か所にある | 1か所にまとめる |
| **過剰な抽象化** | 実装が1つしかないのにインターフェースと Factory | 直接呼び出しに戻す |
| **過剰な防御** | 型で保証されているのに null チェック、何もしない try-catch | 削除（エラーは適切な層でまとめて処理） |
| **使われていない設定・オプション** | 誰も使っていない引数やフラグ | 削除 |
| **不要な依存パッケージ** | 標準機能で済むのにライブラリを追加 | 削除 |
| **ラッパーのラッパー** | A は B を呼ぶだけ、B は C を呼ぶだけ | 中間層をなくす |
| **命名・構造の不統一** | `getUser` / `fetchUser` / `loadUser` が混在 | ルールを決めて揃える |

```
src/ 配下を調査し、以下に当てはまる箇所を一覧にしてください。まだ変更はしないでください。
- 重複しているロジック / 実装が1つしかない抽象化 / 薄いラッパー
- 型で保証されているのに行っている冗長なチェック / 握りつぶしている try-catch
各項目に「影響範囲」と「リスク（高・中・低）」を付け、docs/cleanup-candidates.md にまとめてください。
```

## ④ 優先順位をつける：全部はやらない

**「よく変更される × 複雑」な場所を優先する（ホットスポット分析）。**
```bash
git log --since="6 months ago" --name-only --pretty=format: | grep -v '^$' | sort | uniq -c | sort -rn | head -20
```

| 優先度 | 対象 |
|---|---|
| **すぐやる** | デッドコード・未使用パッケージの削除（低リスク・効果が見えやすい） |
| **次にやる** | 頻繁に変更される場所の重複統合・構造整理 |
| **余裕があれば** | 命名の統一、ほとんど触らない箇所の整理 |
| **やらない** | 動いていて、今後も触る予定がないコード |

## ⑤ 小さく簡素化する

### 原則
- **1回の変更は1種類だけ**（「削除だけ」「統合だけ」を混ぜない）
- **振る舞いを変えない**（機能追加・バグ修正とは別の PR）
- **毎回テストを通してからコミット**
- **差分は人間がレビューできる大きさ**（目安は数百行以内）

### 指示の例
```
knip の結果をもとに、未使用のファイルと export を削除してください。
- 1ファイル削除するごとに typecheck と test を実行
- 動的 import や設定ファイルから参照されているものは削除せず報告のみ
```
```
「日付フォーマット処理の重複」を src/lib/date.ts に統合してください。
各呼び出し元の違い（タイムゾーン、書式）がある場合は、置き換えずに先に報告してください。
```
```
PaymentServiceFactory と IPaymentService は実装が1つしかないので、
StripePaymentService を直接使う形に簡素化してください。
```
大きなファイルは、**まず分割計画だけを出させて**、承認してから実装させる。

## ⑥ 再発を防ぐ

### CLAUDE.md にルールを追加
```markdown
# コードの簡潔さに関するルール
- 新しい関数を作る前に、既存の同等の処理がないか検索すること（src/lib/, src/utils/）
- 実装が1つしかない抽象化は作らない
- 型で保証されている値に null チェックを追加しない
- エラーを握りつぶす try-catch を書かない
- 置き換えた古い実装は必ず削除する。「念のため残す」はしない
- 依頼されていない機能・オプション・設定を追加しない
- 新しいパッケージの追加は事前に確認する
```

### CI で自動チェック
| チェック | 効果 |
|---|---|
| `knip` | 未使用コードが増えたら PR が落ちる |
| `jscpd` の閾値 | 重複が増えたら警告 |
| ESLint の `complexity`, `max-lines` | 複雑すぎる関数・巨大ファイルを防ぐ |
| `dependency-cruiser` | 「UI層からDBを直接呼ばない」などの構造ルールを強制 |

### 習慣
- 定期的に**掃除の日**を作る。掃除専用の PR に分ける
- 実装前に「既存コードで再利用できるものはないか」をAIに調べさせる
- レビューで「この差分から削れるものはある？」とAIに聞く

## まとめ

| ステップ | やること | ポイント |
|---|---|---|
| ① 把握 | AIに構成図・データの流れをまとめさせ、ツールで裏付け | 代表的な処理を1本通して理解する |
| ② 安全網 | 今の振る舞いを固定するテスト | テストなしでリファクタしない |
| ③ 発見 | 重複・デッドコード・過剰な抽象化を洗い出す | まず一覧化、いきなり直さない |
| ④ 優先順位 | よく変更される複雑な場所から | 全部はやらない |
| ⑤ 簡素化 | 1種類ずつ、小さく、振る舞いを変えずに | 毎回テストを通してコミット |
| ⑥ 再発防止 | CLAUDE.md のルールと CI | 掃除を習慣にする |

> **「作るのはAI、全体像を持ち、削る判断をするのは人間」**
