# 02. AIへの指示の出し方と前提知識

[← 目次に戻る](README.md)

## 基本の考え方

AIは**優秀だけど、自分のプロジェクトを初めて見る新人**だと考える。
「ログイン機能作っといて」とだけ頼むと、意図と違うものが出てくる。**出力の質は、指示の具体性とコンテキストで決まる。**

---

## 1. 良い指示に含める6つの要素

| 要素 | 内容 | 例 |
|---|---|---|
| **① 目的（Why）** | なぜ作るのか、誰が使うのか | 「ユーザーが退会前にデータをダウンロードできるように」 |
| **② 対象（What）** | 何を作る・変えるのか | 「`/api/export` エンドポイントを追加」 |
| **③ コンテキスト** | 技術スタック、関連ファイル、既存の設計 | 「Next.js 15 + Prisma。`src/lib/auth.ts` の認証を使う」 |
| **④ 制約** | 守るべきルール、やってはいけないこと | 「新しいライブラリは追加しない」「既存APIは変更しない」 |
| **⑤ 完了条件** | 何ができたら終わりか | 「テストが通る」「CSVで全件出力できる」 |
| **⑥ 進め方** | いきなり書くか、先に計画か | 「まず方針を提案して、承認後に実装して」 |

## 2. 悪い例と良い例

### 例1：新機能の追加

❌ 悪い指示
```
ユーザー検索機能を作って
```

✅ 良い指示
```
管理画面にユーザー検索機能を追加してください。

【目的】
サポート担当が問い合わせ対応時にユーザーをすぐ見つけられるようにする

【仕様】
- メールアドレス・氏名で部分一致検索
- 結果は20件ずつページネーション
- 検索は300msのデバウンスをかける

【コンテキスト】
- 既存の一覧画面: src/app/admin/users/page.tsx
- DBアクセスは src/repositories/userRepository.ts に集約されている
- UIは既存の shadcn/ui コンポーネントを使う

【制約】
- ユーザー数は約50万件。LIKE検索で全件スキャンにならないよう注意
- 新しい npm パッケージは追加しない

【完了条件】
- userRepository に検索メソッドを追加し、ユニットテストを書く
- 既存のテストがすべて通る

まず実装方針とインデックスの要否を説明してから、実装に入ってください。
```

### 例2：バグ修正

❌ 悪い指示
```
ログインできないバグ直して
```

✅ 良い指示
```
ログイン時にエラーになるバグを調査・修正してください。

【再現手順】
1. Googleログインを選択
2. 認証後のリダイレクトで500エラー

【エラーログ】
TypeError: Cannot read properties of undefined (reading 'email')
  at handleCallback (src/auth/callback.ts:42)

【発生条件】
- 昨日のデプロイ以降に発生
- メールログインは正常

【お願い】
- 修正前に原因を特定して説明してください
- 対症療法（undefinedチェックを足すだけ）ではなく根本原因を直してください
- 再発防止のテストを追加してください
```

→ エラーメッセージ・再現手順・「いつから」の情報があるだけで、精度が大きく上がる。

### 例3：リファクタリング

```
src/services/orderService.ts（800行）を分割してください。

【方針】
- 注文作成・決済・通知の3つの責務に分ける
- 外部から呼ばれている関数のシグネチャは変えない（振る舞いを変えないリファクタ）

【手順】
1. まず既存の振る舞いを保証するテストが足りているか確認し、不足していれば先に追加
2. テストが通ることを確認してから分割
3. 分割後もテストが全部通ることを確認
```

## 3. 指示のコツ

### やるべきこと
- **大きなタスクは分割する**：「ECサイト作って」ではなく、機能ごとに段階的に
- **先に計画させる**：複雑なタスクは「実装前に方針を出して」と頼み、ズレを早期に直す
- **既存コードを参照させる**：「`UserCard.tsx` と同じ書き方で」と言うと、プロジェクトの流儀に合わせてくれる
- **検証手段を渡す**：「`npm test` で確認して」と伝えると、AI自身が確認・修正まで回す
- **「なぜ」を伝える**：理由が分かると、指示にないケースでも適切に判断できる

### 避けるべきこと
- 曖昧な形容詞だけの指示（「いい感じに」「きれいに」）
- 1回の指示に無関係なタスクを詰め込む
- 出力をレビューせずにそのまま採用する
- 間違えたときに「違う」とだけ言う → **何がどう違うのか**を伝える

### 繰り返し伝えることは CLAUDE.md にまとめる
```markdown
# プロジェクトルール
- TypeScript strict モード。any 禁止
- テストは Vitest。新機能には必ずテストを書く
- DBアクセスは repositories/ 経由のみ
- コミット前に `npm run lint && npm test` を実行
- エラーメッセージはユーザー向けに日本語で
```

## 4. 持っておくべき前提知識

AIに良い指示を出すには、**「何を頼むべきか」と「返ってきたものが正しいか」が分かる知識**が必要。

### ① 指示を出すための知識
| 知識 | なぜ必要か | 例 |
|---|---|---|
| **設計・アーキテクチャ** | どこに何を作るべきか指示できる | 「ロジックはサービス層に、UIには置かない」 |
| **技術用語の語彙** | 的確な言葉で伝えられる | 「デバウンス」「冪等性」「N+1問題」「楽観的ロック」 |
| **使っている技術スタック** | 制約や前提を伝えられる | フレームワークのバージョン差、ライブラリの特性 |
| **要件定義の力** | エッジケースを事前に指定できる | 「空文字のときは？」「同時に更新されたら？」 |

**語彙の差がそのまま出力の差になる。**
- 「連打されても大丈夫にして」→ 曖昧
- 「二重送信防止のため、ボタンを送信中は disabled にし、APIは冪等キーで重複を弾いて」→ 的確

### ② レビューするための知識
| 知識 | AIがよくやるミス |
|---|---|
| **セキュリティ** | SQLインジェクション、XSS、認可チェック漏れ、秘密情報のハードコード |
| **パフォーマンス** | N+1クエリ、不要な再レンダリング、全件取得 |
| **DB・データ設計** | インデックス不足、トランザクション境界の誤り |
| **非同期・並行処理** | await 漏れ、競合状態（レースコンディション） |
| **エラーハンドリング** | エラーを握りつぶす、雑な try-catch |
| **テスト** | 実装に合わせただけの無意味なテスト、モックしすぎ |

### ③ AIそのものの特性（→ 詳しくは [03](03_AIの仕組みと人間の脳との違い.md)）
- **もっともらしい嘘をつく**：存在しないAPIや関数を書くことがある
- **知識に期限がある**：最新バージョンの仕様を知らない場合がある → ドキュメントを渡す
- **指示されたことしかしない傾向**：「テストを通して」と言うとテストを書き換えて通そうとすることもある
- **コンテキストに限りがある**：長い会話では最初の指示を忘れがち → タスクごとに区切る

## 5. 実践的なワークフロー

```
1. 【調査】「この機能に関係するファイルを調べて、今の仕組みを説明して」
      ↓ 自分の理解と合っているか確認
2. 【計画】「〇〇を実装したい。方針を提案して。まだコードは書かないで」
      ↓ 方針をレビュー・修正
3. 【実装】「その方針で実装して。テストも書いて、npm test で確認して」
      ↓
4. 【レビュー】差分を自分で読む。セキュリティ・性能・エッジケースを確認
      ↓ 気になる点を具体的に指摘
5. 【仕上げ】「lint を通して、変更内容をコミットメッセージにまとめて」
```

---

## まとめ

- **良い指示** ＝ 目的・対象・コンテキスト・制約・完了条件・進め方を具体的に伝える
- **前提知識** ＝ 「的確に頼むための語彙と設計力」と「出力を見抜くためのレビュー力」
- **AIの性能を引き出せるかは、エンジニア自身の基礎力しだい**
