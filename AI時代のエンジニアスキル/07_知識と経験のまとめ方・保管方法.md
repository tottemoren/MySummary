# 07. 知識と経験のまとめ方・保管方法

[← 目次に戻る](README.md)

## 結論：「Markdown ＋ Git」を土台にして、一部を外に公開する

```
【手元に貯める】 Markdown ＋ Git（GitHub のプライベートリポジトリ）
      ↓ 育ったものを
【外に出す】     Zenn・Qiita・ブログ・GitHub（公開）
      ↓ 積み重なると
【キャリアに使う】 職務経歴書・ポートフォリオ・面接のネタ
```

### Markdown ＋ Git をすすめる理由
| 理由 | 説明 |
|---|---|
| **AIがそのまま読める** | Claude Code などに自分のノートを読ませて、検索・要約・質問ができる |
| **サービス終了の心配がない** | ただのテキストファイル。10年後も開ける。ツールも乗り換え自由 |
| **エンジニアの普段の道具で扱える** | エディタ、grep、Git の履歴・差分 |
| **公開しやすい** | Zenn や GitHub にそのまま載せられる |

編集アプリは **Obsidian** が定番（中身はただの Markdown、ノート間リンク・グラフ表示あり）。
Notion はチームでの共有向き。個人の蓄積は Markdown、チームは Notion と分けるのもよい。

## 1. 知識は「種類」ごとに分けて貯める

| 種類 | 内容 | 書く量 | タイミング |
|---|---|---|---|
| **① TIL（Today I Learned）** | 今日知った小さなこと | 数行 | 毎日・気づいたとき |
| **② トラブルシューティング** | ハマったエラーと解決方法 | 短め | 解決した直後 |
| **③ How-to・スニペット** | よく使う手順・コマンド・コード | 短め | 2回目に調べたとき |
| **④ 学習ノート** | 技術の体系的なまとめ | 長め | 本や講座を終えたとき |
| **⑤ 設計・判断の記録** | なぜその技術・設計を選んだか | 中 | 判断したとき |
| **⑥ 振り返り・実績ログ** | 何をして、どんな成果が出たか | 中 | 週・月ごと |

**特に大事なのは ② と ⑥。**
- ② は同じエラーで2度ハマらないための、一番すぐ役立つ記録
- ⑥ は転職時に「何をやってきたか」を具体的に語る材料

## 2. フォルダ構成の例

```
my-knowledge/
├── CLAUDE.md                 ← AIにこのノートの使い方を伝える
├── inbox/                    ← とりあえず放り込む場所
├── til/                      ← ① 日々の小さな学び（月ごとに1ファイル）
├── troubleshooting/          ← ② エラーと解決策
├── howto/                    ← ③ 手順・スニペット
├── notes/                    ← ④ 技術ごとの学習ノート
├── decisions/                ← ⑤ 技術選定・設計判断
├── career/                   ← ⑥ 振り返りと実績
│   ├── weekly/
│   ├── achievements.md
│   └── skills-map.md
└── templates/                ← 各種テンプレート
```

**フォルダを細かく分けすぎない。** 迷ったら `inbox/` に入れて、週1回整理すれば十分。

## 3. テンプレート

### ② トラブルシューティング
```markdown
# Next.js で Hydration エラーが出る

- 日付: 2026-10-01
- 環境: Next.js 15.2 / React 19
- タグ: #nextjs #react #error

## 症状
Hydration failed because the initial UI does not match...

## 原因
サーバーとクライアントで `new Date()` の結果が異なっていた。

## 解決方法
日付の表示をクライアントコンポーネントに移し、useEffect 内で計算した。

## 参考
- 公式ドキュメント: https://...

## 学び
サーバーとクライアントで値が変わるもの（日時・乱数・window）は要注意。
```
**環境（バージョン）を必ず書く。** バージョンが変わると解決方法も変わる。

### ⑥ 実績ログ（転職で効く）
```markdown
# 予約キャンセル機能の開発（2026年9月）

## 状況・課題
店舗への電話でのキャンセル連絡が月200件あり、スタッフの負担になっていた。

## 自分の役割
設計・実装・リリースまで一人で担当。

## やったこと
- Claude Code を使った仕様駆動開発で実装
- 同時キャンセルの競合をDB制約で防ぐ設計にした
- E2E テストを整備し、リリース後の不具合ゼロ

## 成果（数字で）
- 電話でのキャンセル連絡が月200件 → 30件に減少
- 開発期間は見積もり3週間 → 1.5週間

## 使った技術
Next.js, Prisma, PostgreSQL, Playwright, Claude Code

## 学び・次に活かすこと
仕様の段階でエッジケースをAIに洗い出させると、手戻りが大きく減った。
```
面接で使われる **STAR 形式**（状況・課題・行動・結果）とほぼ同じ。**数字はその時点で記録する**（後から思い出せない）。

## 4. 習慣にする流れ

| 頻度 | やること | 時間 |
|---|---|---|
| **毎日** | TIL を1〜3行。ハマったエラーを記録 | 5分 |
| **毎週** | `inbox/` を整理。1週間の振り返り | 15〜30分 |
| **毎月** | 実績ログを更新。記事にできそうなものを選ぶ | 30分〜1時間 |
| **半年ごと** | スキルマップ見直し。職務経歴書を更新 | 1〜2時間 |

**完璧を目指さない。** 汚いメモでも、残っていれば後から探せる。

## 5. AIと組み合わせる

### ノートのリポジトリに CLAUDE.md を置く
```markdown
# このリポジトリについて
私（エンジニア）の個人的な技術ノートです。

# 構成
- til/: 日々の学び
- troubleshooting/: エラーと解決策
- career/: 実績と振り返り

# ルール
- 新しいノートは templates/ の形式に合わせる
- タグは #技術名 の形式で付ける
- 回答するときは、どのノートを根拠にしたかファイル名を示す
```

### 使い方の例
```
troubleshooting/ の中から Prisma に関するノートを探して、よくハマっている原因をまとめて
```
```
今週の til/ を読んで、Zenn の記事にできそうなテーマを3つ提案して
```
```
career/ の実績ログをもとに、職務経歴書の「職務内容」欄の下書きを作って
```
```
inbox/ のメモを適切なフォルダに振り分け、テンプレートの形式に整えて
```

> **書くのは人間、整理・検索・再利用はAIに手伝ってもらう。**

## 6. 外に公開する（アウトプット）

効果：**理解が深まる、フィードバックがもらえる、転職で実力の証明になる。**

| 公開先 | 向いている内容 |
|---|---|
| **Zenn / Qiita** | 技術記事。トラブルシューティングや学習ノートを整えたもの |
| **個人ブログ** | 設計の考え方、振り返り、キャリア |
| **GitHub** | 作ったアプリやツール。README を丁寧に |
| **登壇（LT）** | 社内勉強会、コミュニティイベント |

最初は**自分がハマったエラーの解決方法**から書くのがおすすめ（読まれやすく、書くハードルも低い）。
転職では **GitHub・技術記事・実績ログ** の3つがそろっていると強い。

---

## 7. 注意点

- **会社の機密情報は書かない**：社内コード、顧客名、売上などの具体的な数字、社内システム構成。個人ノートでは一般化して書く
- **個人ノートの GitHub リポジトリはプライベートにする**
- **APIキーやパスワードをノートに書かない**（Git の履歴に残ると消すのが大変）
- **公開前に会社の副業・情報発信ルールを確認する**
