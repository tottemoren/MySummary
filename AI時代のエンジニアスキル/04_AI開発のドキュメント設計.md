# 04. AIで運用まで持っていくためのドキュメント設計

[← 目次に戻る](README.md)

## 結論

> **「全部書く」より「AIと人間が迷わない分だけ、正しい場所に、生きた状態で置く」**

WordやExcelで要件定義からDB設計までを作り込む従来型のやり方は、AI開発と相性がよくない。
- **コードとドキュメントがすぐにズレる**（AIは実装が速い）
- **AIが読みにくい**（Excel・スライドはコンテキストにしづらい）
- **書きすぎるとAIが混乱する**（古い情報・矛盾を信じて間違える）

効果的なのは次の3つ。
1. **ドキュメントはリポジトリの中に Markdown で置く**（Docs as Code）
2. **コードで定義できるものはコードを「正」にする**（スキーマ、型、テスト）
3. **AIにドキュメントを書かせ、更新させる**

---

## 1. フェーズごとのドキュメントのレベル

| フェーズ | 必要なもの | 作り込み度 |
|---|---|---|
| **企画・MVP** | プロダクト概要、主要ユースケース、画面イメージ | 軽め（1〜数ページ） |
| **本格開発** | 機能仕様、データモデル、API仕様、設計判断の記録 | 中（機能ごとに1ファイル） |
| **運用** | 運用手順書、障害対応、監視・アラート設計、リリース手順 | しっかり（人間が夜中に読む） |

最初からすべてを揃える必要はない。

---

## 2. おすすめのリポジトリ構成

```
my-product/
├── CLAUDE.md                  ← AIへの常設指示（最重要）
├── docs/
│   ├── product.md             ← プロダクト概要・ユーザー・ゴール
│   ├── glossary.md            ← 用語集
│   ├── architecture.md        ← 全体構成図・技術選定
│   ├── specs/                 ← 機能仕様（機能ごとに1ファイル）
│   ├── adr/                   ← 設計判断の記録
│   └── runbooks/              ← 運用手順書
├── openapi.yaml               ← API仕様（これが「正」）
├── prisma/schema.prisma       ← DB設計（これが「正」）
└── tests/                     ← テスト（振る舞いの「正」）
```

### 従来の資料との対応
| 従来の資料 | AI時代の置き方 |
|---|---|
| 要件定義書 | `docs/product.md` と `docs/specs/*.md` |
| 画面一覧・画面設計 | specs 内に画面ごとの説明と Figma リンク・スクリーンショット |
| API設計書 | **`openapi.yaml`**（型やクライアントを自動生成） |
| DB設計書（ER図） | **スキーマ定義ファイル**（ER図は自動生成） |
| 詳細設計書 | 基本は不要。コードとテストで表現 |
| 議事録・経緯 | **ADR**（何を、なぜ決めたか） |

## 3. 特に効果の高いドキュメント

### ① CLAUDE.md（AIへの常設指示）★最重要
短く保ち、**AIが間違えやすいことだけ**を書く。
```markdown
# プロジェクト概要
飲食店向けの予約管理SaaS。詳細は docs/product.md を参照。

# 技術スタック
- Next.js 15 (App Router) / TypeScript strict
- PostgreSQL + Prisma
- テスト: Vitest（ユニット）、Playwright（E2E）

# コマンド
- 作業完了前に必ず `pnpm lint && pnpm typecheck && pnpm test` を実行

# 設計ルール
- DBアクセスは src/repositories/ 経由のみ
- API仕様は openapi.yaml が正。変更時は先にここを更新する
- 日時はすべてUTCで保存し、表示時にJSTへ変換
- 金額は整数（円）で扱う。floatは使わない

# 注意事項
- 予約の重複は必ずDBの一意制約で防ぐ
- 新しい設計判断をしたら docs/adr/ に記録する
```

### ② 機能仕様（Spec）：機能ごとに1ファイル
**実装の前に、AIと一緒に仕様を書く**（仕様駆動開発 / Spec-Driven Development）。
```markdown
# 002: 予約キャンセル機能

## 目的
ユーザーが自分で予約をキャンセルできるようにし、店舗の電話対応を減らす。

## 仕様
- 予約日時の24時間前まで：無料でキャンセル可能
- 24時間を切ったら：店舗設定のキャンセル料が発生
- 予約日時を過ぎたら：キャンセル不可
- キャンセル時、ユーザーと店舗にメール通知

## API
- `POST /reservations/{id}/cancel`

## エッジケース
- 同時に2回キャンセル → 2回目は409を返す

## 完了条件
- [ ] すべてのケースにテストがある

## 対象外（今回はやらない）
- キャンセル料のオンライン決済
```
**「対象外」を書くのがコツ。** AIは頼んでいないことまで実装しがち。

### ③ ADR（Architecture Decision Record）
**「なぜそうしたか」**を残す。ないと、AIが過去の判断をひっくり返すことがある。
```markdown
# 0003: 予約の重複チェックはDB制約で行う
## 状況
同時アクセスで同じ枠に2件の予約が入る事故が発生した。
## 決定
(store_id, slot_start) に一意制約を設ける。
## 理由
アプリ側のチェックだけでは競合状態を防げないため。
## 却下した案
アプリ側でロック → 複数インスタンス構成で機能しない
```

### ④ 用語集（glossary.md）
ドメイン用語の定義を揃えると、AIが変数名やUI文言を統一してくれる。
```markdown
| 用語 | 英語（コード上） | 定義 |
|---|---|---|
| 予約 | reservation | ユーザーが確保した来店枠 |
| 枠 | slot | 店舗が公開している予約可能な時間帯 |
```

### ⑤ テスト：最強の「仕様書」
テストは**実行できる仕様書**。AIが「何が正しいか」を自分で確認できる。
```typescript
describe('予約キャンセル', () => {
  it('24時間以上前なら無料でキャンセルできる', ...)
  it('24時間を切るとキャンセル料が発生する', ...)
  it('二重キャンセルは409エラーになる', ...)
})
```

## 4. ドキュメント以外で効果的なやり方

1. **仕様をAIと一緒に作る**：「実装はまだしないで。決めておくべきことやエッジケースを質問形式で洗い出して」と頼む
2. **小さく縦に切って作る**：1機能ずつ DB → API → 画面 → テストまで通して完成させる
3. **検証の自動化を最初に整える**：型チェック、Linter、テスト、CI、スキーマからの型自動生成。「テストが通るまで自分で直して」と任せられる状態を作る
4. **ドキュメントの更新もAIに任せる**：CLAUDE.md に「実装したらドキュメントも更新する」と書く
5. **AIにレビューさせる**：観点（セキュリティ、競合状態、エラー処理）を指定する
6. **繰り返す作業はスキルやコマンドにする**：「新機能の仕様を作る手順」「リリース前チェック」など

---

## 5. 運用フェーズで必要なもの

| ドキュメント・仕組み | 内容 |
|---|---|
| **Runbook（運用手順書）** | デプロイ、ロールバック、DBマイグレーションの手順 |
| **障害対応手順** | 症状ごとの確認と対処の手順 |
| **監視・アラート設計** | 何を監視し、どの閾値で誰に通知するか |
| **ログ設計** | 何をログに出すか（個人情報は出さない） |
| **ポストモーテム** | 障害の振り返り。原因と再発防止策 |

Runbook があれば、**障害時にAIにログと Runbook を渡して一緒に調査**できる。

---

## 6. 全体の流れ

```
【立ち上げ】
 product.md・CLAUDE.md・用語集を作る
 技術スタックとCI（型・lint・テスト）を整える
      ↓
【機能ごとのループ】
 ① AIと対話して仕様を固める → specs/xxx.md
 ② スキーマ（API・DB）を先に更新
 ③ テストを書く（またはAIに書かせてレビュー）
 ④ AIに実装させ、テストが通るまで回す
 ⑤ 人間がレビュー（＋AIレビュー）
 ⑥ ドキュメント・ADRを更新してマージ
      ↓
【運用】
 Runbook・監視・障害対応手順を整備
 障害が起きたらポストモーテム → CLAUDE.md や ADR に反映
```
