# 03. 言語・フレームワークごとのバックエンド構成

[← 目次に戻る](README.md)

Spring Boot（Java）の知識を土台に、Ruby（Rails）・PHP（Laravel）・Go のバックエンドを読むための対応表と注意点。

---

## どの言語でも、リクエストが通る順番はほぼ同じ

```
リクエスト → ルーティング → ミドルウェア → コントローラー → (ビジネスロジック) → データアクセス → DB
```

Spring Boot の4層は、この流れを**きっちり分けるスタイルの1つ**。
言語ごとに違うのは、**各層をどこまで分けるか**と、**部品をどうつなぐか**。

---

## Spring Boot との対応表

| Spring Boot | Ruby（Rails） | PHP（Laravel） | Go（標準的な書き方） |
|---|---|---|---|
| `@GetMapping` などのルート定義 | `config/routes.rb` に集約 | `routes/web.php`、`routes/api.php` に集約 | `main.go` などで手書き登録 |
| Filter / Interceptor | `before_action`、Rackミドルウェア | Middleware | `http.Handler` を包む関数 |
| Controller | Controller | Controller（Livewire コンポーネントも） | Handler |
| Service | **基本は置かない**（Modelに書く） | 任意（Service、Action など） | Service（置くことが多い） |
| Entity + Repository | **Model 1つにまとめる**（Active Record） | **Model 1つにまとめる**（Eloquent） | 構造体 + Store/Repository |
| `@Autowired`（DI） | なし（規約で自動的につながる） | サービスコンテナ（Springに近い） | **コンストラクタ関数で手渡し** |
| Flyway / Liquibase | Migration | Migration | 外部ツール（golang-migrate など） |

---

## 知っておくべき4つのポイント

### 1. Active Record（Ruby と PHP で一番の違い）

Spring では「データの入れ物（Entity）」と「保存係（Repository）」が別クラス。
Rails（ActiveRecord）と Laravel（Eloquent）では、**1つの Model が両方を兼ねる**。

```ruby
# Rails
article = Article.find(1)
article.title = "新しいタイトル"
article.save
```

「Repository はどこ？」と探して迷わないこと。**Repository はない、Model がその役**。

### 2. 「規約」か「明示」か

- **Rails**：ファイル名と場所が規約通りなら自動でつながる。設定はほぼ書かない。便利だが**つながりがコードに書かれていない**ので初見では魔法に見える → Rails の規約自体を知る必要がある
- **Laravel**：Rails に近いが DI の仕組みがあり、Spring に少し近い
- **Go**：魔法がほぼない。**依存関係は全部コードに書いて手で渡す**。冗長に見えるが、読めば全部分かるので Spring 経験者には実は読みやすい

### 3. ビジネスロジックの置き場所は流派による

- **Spring**：Service に置くのが定番
- **Fizzy（37signals の Rails）**：Service 層をあえて作らず、Model と Concern（機能ごとに切り出した部品）に書く
- **Laravel**：Service、Action などプロジェクトごとにばらばら
- **Go**：handler → service → store の3層が多く、Spring に近い

**コードレビューでは、まず「どの流派か」を見極める**。Spring の基準で「Service 層がない」と指摘すると的外れになることがある。

### 4. 型の違い

- **Ruby、PHP**：動的型付け（PHP は型宣言を書けるが任意）。IDE で定義に飛びにくく、実行時にメソッドを作る仕組み（メタプログラミング）もあり、**定義元を追いにくい**ことがある → grep や AI を活用する
- **Go**：Java と同じ静的型付けだが、**クラスも継承もない**。構造体と interface だけ。エラーは例外ではなく**戻り値で毎回返す**（`if err != nil` が多い）

---

## 新しいリポジトリを開いたときに見る順番

1. **入口**：どこから起動するか（Rails は `config/`、Laravel は `public/index.php`、Go は `cmd/` や `main.go`）
2. **ルート定義**：どの URL がどこにつながるか
3. **コントローラー（handler）を1つ**
4. **Model（store）**：DB との接点
5. **テスト**：使い方の実例がまとまっている

---

## おすすめの比較方法

RealWorld には Spring Boot 版もあるので、**Spring Boot 版と Rails 版・Laravel 版・Go 版の同じ機能（記事の投稿など）を並べて読む**と、上の表の違いを一番はっきり体感できる。

## 比較コード例：「記事を作成する」API を4つの言語で書く

同じ機能（ログイン中のユーザーが記事を作成し、`201 Created` で返す）を書き比べる。
**説明のための簡略版**で、そのまま動く完全なコードではない。

### Spring Boot（Java）

```java
// Controller：受け取って、Serviceに頼んで、返す
@RestController
@RequestMapping("/api/articles")                  // ルーティング
public class ArticleController {

    private final ArticleService articleService;

    public ArticleController(ArticleService articleService) {   // DI（コンストラクタ）
        this.articleService = articleService;
    }

    @PostMapping
    public ResponseEntity<ArticleResponse> create(
            @Valid @RequestBody CreateArticleRequest request,    // DTO + 入力検証
            @AuthenticationPrincipal User currentUser) {         // Filterが確認したログイン中のユーザー

        Article article = articleService.create(currentUser, request.title(), request.body());
        return ResponseEntity.status(HttpStatus.CREATED).body(ArticleResponse.from(article));
    }
}

// Service：ビジネスロジック
@Service
public class ArticleService {

    private final ArticleRepository articleRepository;

    public ArticleService(ArticleRepository articleRepository) {
        this.articleRepository = articleRepository;
    }

    @Transactional
    public Article create(User author, String title, String body) {
        return articleRepository.save(new Article(author, title, body));
    }
}
```

### Rails（Ruby）

```ruby
# config/routes.rb ：ルーティングは1ファイルに集約
namespace :api do
  resources :articles, only: [:create]
end

# app/controllers/api/articles_controller.rb
class Api::ArticlesController < ApplicationController
  before_action :authenticate_user!   # Controllerの手前の共通チェック（認証。実装はアプリによる）

  def create
    article = current_user.articles.build(article_params)   # ログイン中のユーザーの記事として作る
    if article.save                                         # Model自身が保存する（Active Record）
      render json: article, status: :created
    else
      render json: { errors: article.errors }, status: :unprocessable_entity
    end
  end

  private

  # 受け取ってよい項目だけを許可する（DTOの役割。Strong Parameters）
  def article_params
    params.require(:article).permit(:title, :body)
  end
end

# app/models/article.rb ：Entity + Repository + 入力検証を兼ねる
class Article < ApplicationRecord
  belongs_to :user
  validates :title, presence: true
end
```

- Service 層がなく、**DI もない**（`current_user` や `Article` は規約で使える）
- 入力検証は **Model に書く**

### Laravel（PHP）

```php
// routes/api.php ：ルーティング + ミドルウェア（認証）
Route::middleware('auth:sanctum')->post('/articles', [ArticleController::class, 'store']);

// app/Http/Controllers/ArticleController.php
class ArticleController extends Controller
{
    public function store(Request $request)
    {
        // 入力検証（ここで通らなければ自動で 422 が返る）
        $validated = $request->validate([
            'title' => 'required|string|max:255',
            'body'  => 'required|string',
        ]);

        // ログイン中のユーザーの記事として作る（Model自身が保存する：Eloquent）
        $article = $request->user()->articles()->create($validated);

        return response()->json($article, 201);
    }
}

// app/Models/Article.php
class Article extends Model
{
    protected $fillable = ['title', 'body'];   // 一括代入してよい項目だけ（マスアサインメント対策）

    public function user()
    {
        return $this->belongsTo(User::class);
    }
}
```

- Rails とよく似ている。入力検証は **Controller（または Form Request クラス）**に書くことが多い

### Go（標準ライブラリ net/http）

```go
// main.go ：部品を手で組み立てて、ルーティングを登録する
func main() {
    db := openDB()
    store := &ArticleStore{db: db}
    handler := &ArticleHandler{store: store}   // DI：全部手で渡す

    mux := http.NewServeMux()
    mux.Handle("POST /api/articles", requireAuth(http.HandlerFunc(handler.Create)))   // ミドルウェアで包む
    http.ListenAndServe(":8080", mux)
}

// handler.go ：Controllerに当たる
type ArticleHandler struct {
    store *ArticleStore
}

type createArticleRequest struct {   // DTOに当たる
    Title string `json:"title"`
    Body  string `json:"body"`
}

func (h *ArticleHandler) Create(w http.ResponseWriter, r *http.Request) {
    var req createArticleRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        http.Error(w, "invalid request", http.StatusBadRequest)
        return
    }
    if req.Title == "" {
        http.Error(w, "title is required", http.StatusUnprocessableEntity)
        return
    }

    userID := userIDFromContext(r.Context())   // ミドルウェアが入れておいたログイン中のユーザー
    article, err := h.store.Create(r.Context(), userID, req.Title, req.Body)
    if err != nil {                            // エラーは戻り値で毎回確認する
        http.Error(w, "internal error", http.StatusInternalServerError)
        return
    }

    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusCreated)
    json.NewEncoder(w).Encode(article)
}

// store.go ：Repositoryに当たる。SQLを自分で書く
func (s *ArticleStore) Create(ctx context.Context, userID int64, title, body string) (*Article, error) {
    // ? はプレースホルダ。値をSQLの一部として解釈させない（SQLインジェクション対策）
    res, err := s.db.ExecContext(ctx,
        "INSERT INTO articles (user_id, title, body) VALUES (?, ?, ?)",
        userID, title, body)
    if err != nil {
        return nil, err
    }
    id, err := res.LastInsertId()
    if err != nil {
        return nil, err
    }
    return &Article{ID: id, UserID: userID, Title: title, Body: body}, nil
}
```

- 魔法がなく、**全部が書いてある**ので長いが、上から読めば全部分かる
- `if err != nil` で**エラーを毎回その場で扱う**

### 4つを並べて見る

| 役割 | Spring Boot | Rails | Laravel | Go |
|---|---|---|---|---|
| ルーティング | `@PostMapping` | `routes.rb` | `routes/api.php` | `mux.Handle(...)` |
| 認証チェック | Spring Security の Filter | `before_action` | `middleware('auth:...')` | `requireAuth(...)` で包む |
| 受け取る項目の限定 | DTO（`CreateArticleRequest`） | `permit(:title, :body)` | `validate` / `$fillable` | リクエスト用の構造体 |
| 入力検証 | `@Valid` + DTOの注釈 | Model の `validates` | `$request->validate` | 自分で `if` を書く |
| ログイン中のユーザー | `@AuthenticationPrincipal` | `current_user` | `$request->user()` | context から取り出す |
| 保存 | Repository の `save` | Model の `save` | Model の `create` | SQL を自分で書く |
| DI | コンストラクタ（自動） | なし | サービスコンテナ | 手で渡す |

**書き方は違っても、「誰か確認 → 受け取る項目を限定 → 検証 → ログイン中のユーザーとして保存 → 201 で返す」という流れと、守っているセキュリティの要点は同じ。**
→ [04 セキュリティ](04_セキュリティの基本.md) の「Entity の直受け」「`userId` を信じない」が、各言語でどう解決されているかが見える。
