# 09. フロントエンド側の観点

[← 目次に戻る](README.md)

01〜08 はバックエンド中心だったので、フロントエンド（React など）側で押さえるべき基本を整理する。
※ 「Rebuildでの例」は 2026-10-07 時点の RebuildReact のコード。

---

## 大原則：フロントエンドのコードは、利用者の手の中にある

- フロントエンドのコード（JavaScript）は、**利用者のブラウザにまるごと送られる**
- 利用者は開発者ツールで、**中身を読めるし、書き換えられるし、保存されている値も変えられる**

そのため：

> **フロントエンドの制限は「使いやすさ（UX）」のため。データを守る「セキュリティ」はサーバーの仕事。**

| フロントエンドでやること | サーバーでやること |
|---|---|
| 入力ミスをその場で知らせる | 入力を必ず検証する |
| 権限のない操作のボタンを隠す | 権限を必ず確認する |
| 未ログインならログイン画面に誘導する | 未ログインならデータを返さない |

**両方やる。ただし守りの本体はサーバー。**

---

## 1. 画面の出し分けは守りではない

**Rebuildでの例**（`components/auth/ProtectedRoute.tsx`）

```tsx
const loginUser = localStorage.getItem("loginUser");

if (!loginUser) {
    return <Navigate to="/" />;   // 未ログインならトップへ
}
return <Outlet />;
```

- 未ログインの人をログイン画面に誘導する**UXとしては正しい**
- ただし開発者ツールで `localStorage.setItem("loginUser", "{}")` と打てば通過できる
- 通過されても困らないように、**データはサーバーが守る**必要がある（→ [04](04_セキュリティの基本.md)・[08](08_HTTPと認証の仕組み.md)）

---

## 2. フロントエンドに秘密情報を置かない

**Rebuildでの例**
```ts
fetch(`${import.meta.env.VITE_API_BASE_URL}/api/memos`)
```

- Vite の `VITE_` で始まる環境変数は、**ビルド時に JavaScript の中に埋め込まれ、誰でも読める**
- API の URL のように**公開されても困らない値**ならよい（Rebuild はこの使い方）
- **API キー、パスワード、秘密鍵は絶対に置かない**。秘密が必要な処理は、サーバー側で行う

---

## 3. XSS（クロスサイト・スクリプティング）

**利用者が入力した文字列に仕込まれたスクリプトが、他の人のブラウザで実行されてしまう攻撃。**
実行されると、その人として操作されたり、localStorage の中身を盗まれたりする。

### ✅ React は基本的に守ってくれる

```tsx
<p>{memo.content}</p>   // <script> が入っていても、ただの文字として表示される
```

`{}` で埋め込んだ値は、React が**自動で無害化（エスケープ）**する。

### ⚠️ React でも危ないところ

| 書き方 | 危険の理由 |
|---|---|
| `dangerouslySetInnerHTML` | 文字列を HTML として解釈する。名前の通り危険 |
| `<a href={userInput}>` | `javascript:...` という URL を入れられるとクリックで実行される |
| 利用者がアップロードした HTML・SVG を同じドメインで表示 | ファイルの中のスクリプトが動きうる（→ [04](04_セキュリティの基本.md) のファイル種別の話） |

**Rebuild**：`dangerouslySetInnerHTML` は使われていない ✅

---

## 4. ブラウザに何を保存するか

**Rebuildでの例**（`pages/LoginPage/LoginPage.tsx`）

```tsx
localStorage.setItem("loginUser", JSON.stringify(user));
```

- ログイン時に返ってきたユーザー情報を localStorage に保存している
- サーバー側の `@JsonIgnore` によって**パスワードは含まれていない** ✅
- 将来トークンを保存する場合、**localStorage は XSS があると読まれる**ので、HttpOnly Cookie と比べて選ぶ（→ [08](08_HTTPと認証の仕組み.md)）

---

## 5. 状態（state）の置き場所

フロントエンドでは「データをどこに持つか」が設計の中心になる。

| 種類 | 例 | 正しい持ち主 |
|---|---|---|
| **サーバーのデータ** | メモ、ストーリー、ユーザー情報 | **サーバー（DB）が正**。画面は写しを持っているだけ |
| **画面の一時的な状態** | 入力中の文字、モーダルの開閉 | コンポーネントの `useState` |
| **URL** | 表示中のページ、検索条件 | URL（共有・再読み込みしても同じ画面になる） |
| **ブラウザ保存** | ログイン状態、設定 | localStorage / Cookie |

**ポイント：同じデータの「正（Single Source of Truth）」を1つに決める。**
写しを複数の場所に持つと、片方だけ更新されて**表示が食い違う**。

**Rebuildでの例**：ユーザー情報はサーバーと localStorage の両方にある。プロフィール画像を変えたとき、`Header.tsx` で localStorage も更新している（写しの更新を忘れていない ✅）。写しが増えるほど、こうした更新漏れのリスクが増える。

## 6. API呼び出しを1か所にまとめる

**Rebuildでの例**：各ページで直接 `fetch` を書いている。

```tsx
// HomePage.tsx
fetch(`${import.meta.env.VITE_API_BASE_URL}/api/memos`)
// MemoPage.tsx
fetch(`${import.meta.env.VITE_API_BASE_URL}/api/memos`)
// StoryCreatePage.tsx
fetch(`${import.meta.env.VITE_API_BASE_URL}/api/memos`)
```

[05](05_リファクタリングとリーダブルコード.md) の**重複**と同じ問題：

- URL を変えるとき、全ページを直す必要がある
- 将来、認証トークンをヘッダーに付けることになったら、**全 fetch に付け忘れなく足す**必要がある
- エラー処理（401 ならログイン画面へ、など）もページごとにばらばらになる

> 案：API 呼び出しを専用のファイルにまとめる。
> ```ts
> // api/memos.ts
> export function fetchMemos(): Promise<Memo[]> {
>   return apiClient.get("/api/memos");   // ベースURL・認証ヘッダー・エラー処理は apiClient に1回だけ書く
> }
> ```
> 画面側は `fetchMemos()` を呼ぶだけになる。

## 7. 利用者に状態を伝える

BtoC のアプリでは、ここが体験の質を大きく左右する。

- **読み込み中**：何も表示されないと「壊れた？」と思われる → ローディング表示
- **失敗したとき**：何が起きて、どうすればいいかを伝える（「通信に失敗しました。再試行」）
- **二重送信の防止**：送信ボタンを押した後は、完了まで押せないようにする（POST は冪等でないので、2回押すと2つできる → [06](06_設計の考え方.md)）
- **空の状態**：データが0件のときに、次に何をすればいいかを示す

## まとめ

| 観点 | 問い |
|---|---|
| 守りの分担 | その制限はUXか、セキュリティか。セキュリティならサーバーでもやっているか |
| 秘密情報 | フロントエンドに公開されて困る値を置いていないか |
| XSS | 利用者の入力を HTML として解釈していないか |
| 保存場所 | ブラウザに何を、どこに保存しているか |
| 状態 | そのデータの「正」はどこか。写しが食い違わないか |
| API呼び出し | 呼び出し・認証・エラー処理が1か所にまとまっているか |
| 体験 | 読み込み中・失敗・二重送信・空の状態を利用者に伝えているか |
