# 01. APIとは何か

[← 目次に戻る](README.md)

## よくある誤解

「APIはバックエンドの処理の一塊」と思いがちだが、少しずれている。

**APIは「処理そのもの」ではなく、「処理を外から使うための窓口と、その使い方の約束」。**

---

## レストランでたとえる

| レストラン | Webアプリ |
|---|---|
| **メニューと注文の決まり** | **API** |
| 厨房での調理 | バックエンドの処理（APIの実装） |
| お客さん | フロントエンド、スマホアプリ、CLI、他のサービス |

- お客さんはメニューを見て注文するだけで、厨房の中は知らない
- 厨房がシェフや調理法を変えても、**メニューと出てくる料理が同じなら、お客さんには影響がない**

---

## Web APIで決めること

| 項目 | 例 |
|---|---|
| **どこに** | URL（`/api/articles`） |
| **何をするか** | メソッド（GET＝取得、POST＝作成、PUT＝置き換え、DELETE＝削除） |
| **何を渡すか** | リクエストの形（タイトル、本文など） |
| **何が返るか** | レスポンスの形、成功・失敗の表し方（ステータスコード、エラーの中身） |
| **誰が使えるか** | 認証の方法 |

その裏でDBに保存したり計算したりするのは、**APIの実装**であって、API自体ではない。

---

## 実例：RealWorld

RealWorldは**API（約束）が1つだけ決まっていて**、その実装が Rails、Go、Node.js、Spring Boot など多数ある。だからフロントエンドはどのバックエンドとも組み合わせられる。

→ 「APIと処理は別物」ということを、そのまま形にしたプロジェクト。

---

## なぜこの区別が大事か

**APIは一度公開すると簡単に変えられない。**

- クラウドサービスなら、CLI・Terraform・お客さんのスクリプトが同じAPIに依存している。形を変えると一斉に壊れる
- スマホアプリなら、古いバージョンを使い続ける人がいる。APIを変えるとその人たちのアプリが動かなくなる

だから **「APIの設計」とは、処理を書くことではなく、長く守り続けられる約束を決めること**。
中の処理は後から直せるが、約束は直しにくい。

---

## Web以外の「API」

意味は同じく「窓口と約束」。

- ライブラリの関数の呼び方
- ブラウザが提供する機能（位置情報、カメラなど）の呼び方
- OSが提供する機能の呼び方

---

## まとめ

- APIは**窓口と約束**、処理は**実装**
- 約束を守れば、実装は自由に変えられる
- 約束（API）を変えるのは高くつくので、最初の設計が大事
