# 05. リファクタリングとリーダブルコード

[← 目次に戻る](README.md)

※ 「Rebuildでの例」は 2026-10-07 時点のコード。

---

## 言葉の意味

- **リファクタリング**：**動作を変えずに**、コードの中身（構造）だけを整えること。機能追加やバグ修正はリファクタリングではない
  - たとえ：住める状態のまま、家具の配置を使いやすく変える模様替え
- **リーダブルコード**：他の人（や未来の自分）が、**短い時間で正しく理解できる**コード

**コードは書く時間より読まれる時間の方がずっと長い。** 1回書いたコードは、修正や機能追加のたびに何十回も読まれる。

---

## 1. 名前：名前だけで中身が分かるか

✅ **良い例**（`MangaPanelService`）
```java
getPanelsByStoryId(Long storyId)
replacePanels(Long storyId, List<MangaPanel> panels)
findByStoryIdOrderByZIndexAsc(storyId)
```
`save` ではなく `replace` にしたことで「既存のものは消える」ことまで伝わる。

⚠️ **直す余地がある例**（`RebuildJavaController`）
- 中身は「ログイン」「メモの操作」「動作確認用トップページ」
- 名前はアプリ名だけ → **名前から中身が分からない**。ログイン処理を探すとき見つからない

> 案：役割ごとに `AuthController` と `MemoController` に分ける。

**名前を付けにくいときは、役割を詰め込みすぎているサイン。**

---

## 2. 重複：同じコードが2か所にないか

⚠️ **直す余地がある例**：ファイルアップロード処理が `UserController` と `FolderController` に**ほぼ同じ約30行**ずつある（空チェック → 拡張子取得 → UUIDで命名 → フォルダ作成 → 保存）。

**問題**：「拡張子を画像だけに制限する」というセキュリティ修正が必要になったとき、**2か所とも直す必要があり、片方を忘れると穴が残る**。

> 案：共通部分を1つのクラスに切り出す。
> ```java
> @Service
> public class FileStorageService {
>     // 画像を保存して、保存したファイル名を返す
>     public String saveImage(MultipartFile file, Path directory) {
>         // 空チェック、拡張子の確認、UUIDでの命名、保存をここに1回だけ書く
>     }
> }
> ```

**重複をなくすと、修正が1か所で済み、修正漏れのバグがなくなる。**（DRY：Don't Repeat Yourself）

---

## 3. マジックナンバー・直書きの値

**コードに直接書かれた、意味や出どころが分からない値。**

⚠️ **直す余地がある例**（`MaterialController`）
```java
Files.deleteIfExists(Paths.get("uploads", relativePath));
```
- アップロード時は設定ファイル（`file.materials-upload-dir`）から保存先を読むのに、**削除時は `"uploads"` を直書き**
- 設定で保存先を変えると、**保存は新しい場所、削除は古い場所を探す**。エラーは無視されるので、**ファイルが残り続けても誰も気づかない**

他の例：`UserService` の `"USER"`（権限名）、招待コード。

> 案：保存先は設定から読む、権限名は定数や enum にする。**同じ値の出どころを1か所にする。**

---

## 4. コメント：「何を」ではなく「なぜ」を書く

✅ **良い例**（`MangaPanelService.replacePanels`）
```java
/**
 * 「編集して保存」を単純化するため、既存分を削除してから新しい配置を保存し直す方式にしている。
 */
```
「削除してから保存している」（何を）はコードで分かる。**「なぜ更新ではなく作り直すのか」**はコードから分からない → それを書いている。

✅ 他の良い例：`User` の「フロントエンドへは絶対に返さない」、`SecurityConfig` の方針説明。

❌ **悪いコメント**
```java
// ユーザーを保存する
userRepository.save(user);
```
コードの繰り返しで情報が増えない。コードを変えたときに直し忘れると**コメントが嘘をつく**。

---

## 5. 一貫性：同じことは同じ書き方で

| 項目 | Rebuildで混在している書き方 |
|---|---|
| DI | `@Autowired`（Story、Dialogue）とコンストラクタ（Folder、User） |
| URL | `/api/...` で始まるものと始まらないもの |
| CORS | 許可サイトを限定したものと全許可のもの |
| 層 | Service を通すもの（Story）と Repository 直接（Folder） |

一つひとつは動くが、**読む人は毎回「なぜここだけ違う？」と考えて止まる**。理由のない違いは読む人の時間を奪うだけ。

**リーダブルなコードとは、驚きの少ないコード。** 1ファイル理解すれば、他のファイルも同じように読めるのが理想。

---

## 6. 1つの関数に1つの仕事

⚠️ `UserController.uploadProfileImage` が1つで全部やっている：
空チェック → 拡張子取得 → ファイル名作成 → フォルダ作成 → 保存 → URL作成 → DB更新

**Controller の本来の仕事は「受け取って、誰かに頼んで、結果を返す」こと。**

```java
// リファクタリング後のイメージ
public ResponseEntity<?> uploadProfileImage(Long id, MultipartFile file) {
    String fileName = fileStorageService.saveImage(file, profileImageDir);
    User user = userService.updateProfileImage(id, "/uploads/profile-images/" + fileName);
    return ResponseEntity.ok(user);
}
```

## 7. 見た目：読みやすい改行

⚠️ 短い処理が不必要に複数行に分かれている例：
```java
return dialogueService
        .getDialoguesByStoryId(
                storyId);
```
```java
return dialogueService.getDialoguesByStoryId(storyId);   // 1行で読める
```
見た目は**フォーマッター（自動整形ツール）**で機械的にそろえるのが一般的。人が気にするべきことではない。

---

## リファクタリングを安全に行う3つのルール

1. **テストがあること**：変更前後でテストが同じように通れば、動作が変わっていないと確認できる。**テストはリファクタリングの命綱**
2. **小さく進めること**：「名前を変える」「1つ切り出す」と1つずつ。そのたびにテストを実行
3. **機能追加と混ぜないこと**：混ぜるとバグが出たときに原因が分からない（1つのブランチ・PRは1つの目的）

## AIがコードを読める時代に、リーダブルコードは必要か

**結論：必要。むしろ重要になった部分がある。ただし大事な点は変わった。**

### 今も（以前より）大事な理由

1. **AIも読みにくいコードに惑わされる**
   - AIは全体を一度に読まず、**名前で検索して関係しそうな部分を読む**ことが多い
   - 名前が中身と合っていないと見落とす。重複があると**片方だけ直して、もう片方を見落とす**
   - 設定と直書きが食い違っていると、どちらが正しいか判断できない
2. **AIは周りのコードをまねる**
   - 書き方が混在していれば、どちらかをまねる。危ない書き方が多ければ新しいコードも危ない形で書く
   - **悪い書き方は AI によって増殖する**
3. **最終的に確認して責任を持つのは人間**
   - AIで書く速度が上がり、**ボトルネックは「書くこと」から「読んで確認すること」に移った**
   - 読みにくいコードは、AIの変更が正しいかを確認する時間を増やし、見落としを生む
4. **「なぜ」はコードから読み取れない**
   - AIはコードが**何をしているか**は読めるが、**なぜそうしたか**は書かれていないと分からない
   - 理由を書いたコメントがないと「非効率なので変えましょう」と意図を壊す提案をしかねない
   - **理由のコメントは、AIへの指示書にもなる**

### 以前より重要でなくなったこと

- 改行やインデントなどの**見た目**（フォーマッターとAIで自動化できる）
- 複雑な処理の**1行1行の読み解き**（AIに説明させられる）

| 以前より重要になった | 以前ほど重要でない |
|---|---|
| 名前（AIの検索の手がかり） | 細かい見た目、改行 |
| 重複をなくす（修正漏れ防止） | 1行1行の読み解き |
| 一貫性（AIがまねる元になる） | |
| 「なぜ」のコメント（AIへの指示書） | |
| テスト（AIの変更を検証する手段） | |

> **AI時代のリーダブルコードは、「人間が速く読めるコード」であると同時に「AIが正しく扱えるコード」。**
