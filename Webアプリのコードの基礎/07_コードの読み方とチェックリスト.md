# 07. コードの読み方とチェックリスト

[← 目次に戻る](README.md)

全ノートの内容を、**他人のコードを読むとき・レビューするとき・自分のコードを見直すとき**に使えるよう、手順と問いの一覧にまとめる。

---

## 読み方の基本

### 1. 全体を上から読まない。1つの機能を入口から出口まで追う

例：
- RealWorld：記事を投稿する
- Fizzy：カードを作る
- Rebuild：コマ配置を保存する

### 2. 新しいリポジトリを開いたら、この順番で場所を探す

1. **入口**：どこから起動するか
2. **ルート定義**：どの URL がどこにつながるか
3. **コントローラー（handler）を1つ**
4. **Model（store / repository）**：DB との接点
5. **テスト**：使い方の実例

### 3. 機能を追うときの5つの問い

1. リクエストはどこで受け取られるか（ルーティング）
2. 認証と権限のチェックはどこで行われるか
3. データはどこで検証され、どこで保存されるか
4. エラーのときは何が返るか
5. **自分のコード（Rebuild）では同じことをどう書いているか**

同じ問いで複数のリポジトリを読むと、違いがそのまま「なぜそう書くのか」の気づきになる。

### 4. まず「流派」を見極める

Service 層を置くか、Model に書くかなどはフレームワークやチームの流派で違う。自分の慣れた基準で「間違い」と決めつけない。→ [03](03_言語・フレームワークごとのバックエンド構成.md)

## チェックリスト

### 構成（→ [02](02_リクエストの流れとSpringBootの基本の仕組み.md)・[03](03_言語・フレームワークごとのバックエンド構成.md)）
- [ ] ルーティング・ミドルウェア・コントローラー・データアクセスがどこにあるか分かる
- [ ] 層の分け方（Service の有無など）がプロジェクト内でそろっている
- [ ] DB の構造変更はマイグレーションで管理されている

### API（→ [01](01_APIとは何か.md)・[06](06_設計の考え方.md)）
- [ ] URL の命名ルールがそろっている
- [ ] メソッド（GET/POST/PUT/DELETE）とステータスコードが HTTP の意味と合っている
- [ ] 一度公開した API を壊さない配慮がある

### セキュリティ（→ [04](04_セキュリティの基本.md)）
- [ ] サーバー側で毎回確かめているか（画面の制限に頼っていないか）
- [ ] 認証：誰かをサーバー自身が判断している（クライアントの `userId` を信じていない）
- [ ] 認可：データの持ち主を確認してから操作している
- [ ] 入力：DTO で受け取る項目を限定している。SQL を文字列連結で作っていない
- [ ] ファイル：拡張子・種類・サイズを許可リストで制限している
- [ ] 出力：パスワードや内部エラーを返していない
- [ ] 秘密情報：コードや Git に鍵・パスワードを書いていない
- [ ] CORS：許可するサイトを限定している（ただし認証の代わりではない）

### 読みやすさ（→ [05](05_リファクタリングとリーダブルコード.md)）
- [ ] 名前だけで中身が分かる
- [ ] 同じ処理が複数か所にない
- [ ] 意味の分からない直書きの値がない
- [ ] コメントは「なぜ」を書いている
- [ ] 同じことは同じ書き方でそろっている
- [ ] 1つの関数が1つの仕事をしている
- [ ] 見た目はフォーマッターで自動整形している

### 設計（→ [06](06_設計の考え方.md)）
- [ ] 途中で失敗しても、データが中途半端に残らない（トランザクション）
- [ ] 大事なデータのルールは DB の制約でも守られている
- [ ] 失敗の種類によって 4xx / 5xx を返し分け、エラーを握りつぶしていない
- [ ] サーバーが消えても、2台に増えても大丈夫（ステートレス）
- [ ] 取り替える予定の部分は、インターフェースで分けてある（予定のないものは分けすぎない）
- [ ] 壊れたら困る部分にテストがある

### HTTPと認証（→ [08](08_HTTPと認証の仕組み.md)）
- [ ] ログイン後、セッションや JWT などの「証拠」で、サーバーが誰かを判断している
- [ ] Cookie を使うなら HttpOnly・Secure・SameSite を付けている
- [ ] Cookie で認証するなら CSRF 対策をしている
- [ ] JWT に秘密の情報を入れていない
- [ ] 通信は HTTPS になっている

### フロントエンド（→ [09](09_フロントエンド側の観点.md)）
- [ ] 画面の制限（ボタンを隠す、ページへの誘導）に、セキュリティを頼っていない
- [ ] フロントエンドに公開されて困る値（APIキーなど）を置いていない
- [ ] 利用者の入力を HTML として解釈していない（`dangerouslySetInnerHTML` など）
- [ ] 同じデータの「正」が1か所に決まっている
- [ ] API 呼び出し・認証ヘッダー・エラー処理が1か所にまとまっている
- [ ] 読み込み中・失敗・二重送信・空の状態を利用者に伝えている
