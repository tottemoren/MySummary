# 08. HTTPと認証の仕組み

[← 目次に戻る](README.md)

[04 セキュリティ](04_セキュリティの基本.md) の「認証」の土台になる知識。
「ログインした状態」が、裏側でどう実現されているかを整理する。

---

## HTTPのリクエストとレスポンスの中身

ブラウザやアプリとサーバーは、**決まった形式の文字のやりとり**をしている。

### リクエスト（送る側）

```http
POST /api/articles HTTP/1.1              ← メソッド・URL
Host: api.example.com                    ← ここから「ヘッダー」（付帯情報）
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...      ← 認証の情報（後述）
Cookie: session_id=abc123                ← Cookie（後述）
                                         ← 空行
{"title": "はじめての記事", "body": "..."} ← ボディ（本文）
```

### レスポンス（返す側）

```http
HTTP/1.1 201 Created                     ← ステータスコード
Content-Type: application/json           ← ヘッダー
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax   ← Cookieを保存させる指示

{"id": 1, "title": "はじめての記事"}      ← ボディ
```

| 部分 | 役割 |
|---|---|
| メソッド・URL | 何をどこに（[06](06_設計の考え方.md) の HTTP の意味） |
| ステータスコード | 結果（200、404 など） |
| **ヘッダー** | 付帯情報。データの形式、認証情報、Cookie など |
| ボディ | 本文のデータ（JSON など） |

ブラウザの開発者ツールの「ネットワーク」タブで、実際のやりとりを見られる。

---

## HTTPは「覚えていない」

**HTTPは、1回ごとのやりとりが独立していて、前のリクエストを覚えていない**（ステートレス）。

そのため「さっきログインした人」をサーバーが知るには、**毎回のリクエストに「自分が誰か」を示す証拠を付けて送る**必要がある。
その証拠の方式が、主に **セッション** と **トークン（JWT）** の2つ。

---

## 方式1：セッション（+ Cookie）

```
① ログイン（ユーザー名・パスワードを送る）
② サーバー：確認OK → 「セッション」を作って保存（例：session_id=abc123 は ユーザー1）
③ サーバー → ブラウザ：Set-Cookie: session_id=abc123
④ 以降、ブラウザは自動で Cookie: session_id=abc123 を毎回付けて送る
⑤ サーバー：abc123 を自分の保存場所で調べて「ユーザー1だ」と判断
```

- **Cookie**：サーバーの指示でブラウザが保存し、**同じサイトへのリクエストに自動で付けて送る**小さなデータ
- 証拠（セッションID）は**ただの番号**。中身（誰か）はサーバー側にある
- たとえ：クロークの番号札。札には番号しか書いておらず、荷物はクローク側にある

---

## 方式2：トークン（JWT）

```
① ログイン
② サーバー：確認OK → 「ユーザー1、有効期限○時まで」という内容に**署名**したトークンを発行
③ クライアントはトークンを保存
④ 以降、毎回 Authorization: Bearer <トークン> ヘッダーを付けて送る
⑤ サーバー：署名が正しいかを検証して「ユーザー1だ」と判断（保存場所を調べなくてよい）
```

- **JWT（JSON Web Token）**：中身（誰か、期限など）と、改ざん防止の**署名**が入った文字列
- 署名はサーバーだけが持つ秘密鍵で作るので、**中身を書き換えると検証で失敗する**
- 中身は暗号化されておらず**誰でも読める**。パスワードなど秘密の情報は入れない
- たとえ：偽造できない印鑑が押された通行証。受付は印鑑を確認するだけでよい

---

## セッションとJWTの比較

| | セッション | JWT |
|---|---|---|
| 「誰か」の情報の置き場所 | サーバー側 | トークン自身の中 |
| サーバーの保存場所 | 必要（メモリ、DB、Redisなど） | 不要 |
| ログアウト・強制無効化 | 簡単（サーバー側で消す） | 難しい（期限まで有効。工夫が必要） |
| サーバーを増やしたとき | セッションを共有する仕組みが必要 | そのまま検証できる |
| よく使われる場面 | ブラウザ向けのWebアプリ | スマホアプリ、外部向けAPI、サービス間通信 |

どちらが正解ということはなく、**用途で選ぶ**。ブラウザだけのWebアプリならセッションの方がシンプルで安全に作りやすいことも多い。

## ブラウザのどこに保存するか

| 保存場所 | JavaScriptから読めるか | 自動で送られるか | 注意点 |
|---|---|---|---|
| **localStorage** | 読める | 送られない（自分で付ける） | **XSS があると盗まれる** |
| **Cookie（HttpOnly 付き）** | **読めない** | 自動で送られる | **CSRF** への対策が必要 |

### Cookie に付ける大事な属性

- **HttpOnly**：JavaScript から読めなくする → XSS で盗まれにくい
- **Secure**：HTTPS のときだけ送る
- **SameSite**：他のサイトから来たリクエストには付けない（Lax / Strict）→ CSRF 対策

---

## CSRF（クロスサイト・リクエスト・フォージェリ）

**Cookie が自動で送られることを悪用して、利用者に意図しない操作をさせる攻撃。**

```
① 利用者が example.com にログイン中（Cookieあり）
② 悪意あるサイトを開くと、裏で example.com に「削除」リクエストを送らせる
③ ブラウザは自動で Cookie を付けるので、サーバーは本人の操作だと思ってしまう
```

対策：Cookie の **SameSite** 属性、**CSRF トークン**（フォームごとに予測できない値を付けて確認する）。

**Rebuildでの関係**：`SecurityConfig` で CSRF 保護を無効にしており、コメントに「Cookie を使わない fetch ベースの API なので不要」とある。Cookie を使っていない今の作りでは筋が通っている。
ただし**将来 Cookie のセッション方式に切り替えるなら、CSRF 対策を有効に戻す必要がある**。

---

## HTTPS

**通信を暗号化する仕組み。** HTTPS でないと、途中の経路（公衆Wi-Fiなど）でパスワードや Cookie、トークンを盗み見られる。
今の Web では**必須**。Cookie の `Secure` 属性も HTTPS が前提。

---

## Rebuildの現状（2026-10-07時点）

```
① ログイン → サーバーはユーザー情報（JSON）を返すだけ
② フロントエンドがそれを localStorage に "loginUser" として保存
③ 以降、リクエストのボディやURLに loginUser.id を入れて送る
④ サーバーは送られてきた userId をそのまま信じる
```

- セッションIDもトークンもないので、**「本当にその人か」を証明するものが何もない**
- localStorage の値も、送る `userId` も、利用者が自由に書き換えられる
- → [04](04_セキュリティの基本.md) の「ログイン後に『誰か』を覚えていない」の正体はこれ

**本来の形**：セッションか JWT のどちらかで「証拠」を発行し、サーバー側では Filter でそれを検証して「ログイン中のユーザー」を決める。Controller はクライアントの `userId` ではなく、その「ログイン中のユーザー」を使う。
