# 06. 設計の考え方

[← 目次に戻る](README.md)

コードを理解するうえで大事な設計の考え方を7つ、「コードを読むときの問い」とセットで整理する。
※ 「Rebuildでの例」は 2026-10-07 時点のコード。

---

## 1. トランザクション：全部成功するか、全部なかったことにするか

**複数のDB操作を1つのまとまりとして扱い、途中で失敗したら全部元に戻す仕組み。**

たとえ：銀行振込。「Aさんから1万円引く」「Bさんに1万円足す」のうち、1つ目だけ成功すると1万円が消える。

**Rebuildでの例**（`MangaPanelService.replacePanels`）
```java
mangaPanelRepository.deleteByStoryId(storyId);   // ① 既存のコマを全部消す
...
return mangaPanelRepository.saveAll(panels);     // ② 新しいコマを保存する
```
①が成功して②が失敗すると、**作ったコマ配置が全部消える**。

- Spring ではメソッドに `@Transactional` を付けると、中の操作が1つのトランザクションになる。Rebuild には `@Transactional` が見当たらなかった
- （未確認）Spring Data JPA では `deleteByStoryId` のような削除メソッドは、トランザクションがないとエラーになることが知られている。実際に動いているかは要確認

**DBとファイルの組み合わせも同じ問題を持つ**
- `MaterialController` は「ファイル削除 → DB削除」の順。DB削除が失敗すると、**DBに素材が残るのに画像ファイルがない**状態になる
- ファイルは DB のトランザクションの外にあるので、**どちらを先にやるか**を設計する必要がある

**問い**：この処理が途中で失敗したら、データはどんな状態で残るか

## 2. データベース設計：ルールをどこで守るか

**データのルール（制約）を、アプリのコードで守るか、DB自身に守らせるか。**

**Rebuildでの例**
- フォルダは `userId` という数字で持ち主を持つが、DB側に「実在するユーザーIDでなければならない」という**外部キー制約**が見当たらない → 存在しないユーザーのフォルダも作れる
- フォルダ削除は「① 素材が残っていないか確認 → ② 削除」。①と②の間に素材が追加されると、**素材が入ったままフォルダが消える**（確認と実行の間のすき間。利用者が増えると起きやすい）
- `init.sql` にフォルダ・素材のテーブルがなく `ddl-auto` で作られている → **DBの正しい構造の置き場所が2か所に分かれている**

**ポイント**：アプリのチェックには**書き忘れやすき間**がありうる。DBの制約は**どこから書き込んでも必ず守られる最後の砦**。大事なルールほど DB にも持たせる。

**問い**：このデータのルールは、コードとDBのどちらで守られているか

## 3. エラー処理の設計

**失敗したときに、何が起きて、誰に何が伝わるかを決めること。**

**Rebuildでの例1**（`UserService`）
```java
.orElseThrow(() -> new IllegalArgumentException("ユーザーが見つかりません: " + userId));
```
ユーザーが見つからないのは**利用者側の間違い**なので本来は `404`。だが例外をどこでも受け止めていないので、Spring は**サーバーの故障（`500`）**として扱う。

**Rebuildでの例2**（`MaterialController`）
```java
} catch (IOException ignored) {
    // ファイルが既に無い場合等は無視し、DBレコードの削除は続行する
}
```
理由のコメントは良いが、権限エラーやディスク故障なども**全部黙って無視され、ログにも残らない**。

**ポイント**
- 失敗の種類でステータスコードを分ける（**利用者の間違いは4xx、サーバーの問題は5xx**）
- **エラーを握りつぶさない**（無視するなら最低限ログに残す）
- Spring では `@ControllerAdvice` で**エラーの扱いを1か所にまとめる**のが一般的

**問い**：失敗したとき、利用者と開発者にはそれぞれ何が見えるか

## 4. HTTPの意味を守る

HTTPのメソッドやステータスコードには**世界共通の意味**がある。守ると、説明を読まなくても動きを予想できる。

| メソッド | 意味 | 何回送っても結果が同じか（冪等性） |
|---|---|---|
| GET | 取得する | 同じ（何も変えない） |
| POST | 新しく作る | **違う**（2回送ると2つできる） |
| PUT | 丸ごと置き換える | 同じ |
| DELETE | 削除する | 同じ |

**冪等（べきとう）**な操作は、通信が途切れて届いたか分からないとき**安心してもう一度送れる**。電波が不安定なスマホアプリでは特に大事。

**Rebuildでの良い例**
- ✅ コマ保存が「丸ごと置き換え」で、`@PutMapping` を使っている → PUT の意味とぴったり
- ✅ 「素材が残っているので削除できない」に `409 Conflict`（現在の状態と矛盾）を使っている

**よく使うステータスコード**

| コード | 意味 |
|---|---|
| 200 OK / 201 Created | 成功 / 作成した |
| 400 Bad Request | リクエストの形がおかしい |
| 401 Unauthorized | 誰か分からない（未ログイン） |
| 403 Forbidden | 誰かは分かるが、してはいけない |
| 404 Not Found | 見つからない |
| 409 Conflict | 今の状態と矛盾する |
| 500 Internal Server Error | サーバー側の問題 |

**問い**：このAPIのメソッドとステータスコードは、HTTPの意味と合っているか

## 5. ステートレス：サーバーに「状態」を持たせない

**サーバー自身の中に、データや状態を溜め込まない。**

**Rebuildでの例**：アップロード画像を**サーバー自身のディスク**（`uploads/`）に保存している。1台なら問題ないが、2台に増やすと：

```
ユーザーがサーバーAに画像をアップロード → Aのディスクに保存
別のユーザーの表示リクエストがサーバーBに届く → Bには画像がない → 表示されない
```

サーバーが壊れて作り直したときも画像が消える。
→ 画像は **S3 のような外部の保存場所**に置き、サーバーには何も溜めない。そうすれば何台に増やしても、入れ替えても大丈夫。

**問い**：このサーバーが突然消えたり、2台に増えたりしても大丈夫か

## 6. 抽象化と依存の向き：「何をするか」と「どうやるか」を分ける

**「何をするか（画像を保存する）」と「どうやるか（ローカルに書く / S3に送る）」を分ける。** Java では**インターフェース**で表す。

```java
// 「何をするか」だけを決めたインターフェース
public interface ImageStorage {
    String save(MultipartFile file);
    void delete(String path);
}

// 「どうやるか」はそれぞれのクラスに
public class LocalImageStorage implements ImageStorage { ... }  // 今
public class S3ImageStorage implements ImageStorage { ... }     // 将来
```

- Controller は `ImageStorage` だけ知っていればよく、中身がローカルか S3 かを気にしない
- 切り替えは DI で渡すクラスを差し替えるだけ。テストでは「保存しない偽物」も渡せる
- 今の Rebuild は保存処理が Controller に直接書かれているので、S3 移行時は全 Controller の書き換えが必要

**やりすぎに注意（YAGNI：You Aren't Gonna Need It）**
- 「将来使うかも」で何でも抽象化すると、複雑になるだけ
- Rebuild は**S3移行が実際に予定されている**ので抽象化する価値がある。予定のないものは不要
- `replacePanels` の「単純化するため」という判断は、**シンプルさを優先した良い設計判断**（KISS：Keep It Simple, Stupid）

**問い**：この部分を別のものに取り替えるとき、どこまで書き換えが必要か

## 7. テストの考え方：何を守るためのテストか

**テストは「このコードはこう動くべき」という約束を、実行できる形で書いたもの。**

**Rebuildの現状**：テストは `FolderApiTest`、`MemoApiTest`、起動確認の3つ。ストーリー、セリフ、コマ、ユーザー登録、ログインは**壊れても気づける仕組みがない**。（1のトランザクションの疑問も、コマ保存のテストがあれば実行するだけで確かめられる）

**どこからテストを書くか**
1. **壊れたら一番困るところ**：ログイン、ユーザー登録（ハッシュ化）、データの保存
2. **これから変更するところ**：リファクタリングや S3 移行の前に、今の動きをテストで固める
3. **過去にバグが出たところ**：同じバグを繰り返さないため

**問い**：このコードが壊れたら、どのテストが教えてくれるか
