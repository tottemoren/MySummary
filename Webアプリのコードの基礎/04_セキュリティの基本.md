# 04. セキュリティの基本

[← 目次に戻る](README.md)

言語を問わず、Webアプリに求められるセキュリティの基本を6つのテーマで整理する。
※ 「Rebuildでの例」は 2026-10-07 時点のコード。バックエンドは未公開なので、本番に出す前に知っておくべきこととして記録している。

---

## 大前提：サーバーは「送られてきたもの」を信用できない

画面（フロントエンド）からしかリクエストは来ない、と思いがちだが、**実際には誰でも、どんな内容でも送れる**。

```bash
curl -X DELETE http://localhost:8080/api/materials/1
```

画面で削除ボタンを自分の素材にしか出していなくても、**サーバー側でチェックしていなければ他人の素材も消せる**。

> **セキュリティの多くは「サーバー側で毎回確かめているか」に帰着する。**

---

## 1. 認証：「あなたは誰？」

**ログインして、相手が誰かを確かめること。**

### ✅ パスワードのハッシュ化
```java
passwordEncoder.matches(request.getPassword(), user.getPassword())
```
- パスワードをそのまま保存せず、**元に戻せない形（ハッシュ）**で保存する。DBが盗まれてもパスワードは分からない
- BCrypt は定番の正しい方法

### ✅ 失敗理由を言い分けない
- ユーザー名が無い場合もパスワードが違う場合も、同じ `401` を返す
- 「そのユーザー名は存在しません」と返すと、**登録済みのユーザー名を攻撃者に教えてしまう**

### ⚠️ ログイン後に「誰か」を覚えていない（Rebuild）
- ログイン後、「さっきログインした人だ」と確かめる仕組み（セッションや JWT）がない
- そのため**リクエストに書かれた `userId` をそのまま信じる**作りになっている → `userId` を書き換えれば他人になれる

> **本来の形**：ログイン成功時にサーバーが「通行証」（セッションID や JWT）を発行し、以降はそれを見て**サーバー自身が**誰かを判断する。クライアントが送る `userId` は信じない。

### ⚠️ ログイン試行回数に制限がない
- 何万回でも試せるので総当たり攻撃が可能 → 本番では**レート制限**を入れる

---

## 2. 認可：「あなたはそれをしてよい？」

**ログインした人が、その操作をしてよいかを確かめること。** 初学者が最も見落としやすく、**実際の事故で最も多い種類**の1つ。
（アクセス制御の不備。IDを書き換えるだけで他人のデータに触れるものを **IDOR** と呼ぶ）

### ⚠️ 持ち主を確認せずに削除している（Rebuild）
```java
@DeleteMapping("/{id}")
public void deleteMaterial(@PathVariable Long id) {
    materialRepository.findById(id).ifPresent(material -> { ... deleteById(id); });
}
```
IDが分かれば誰の素材でも削除できる。IDは連番なので推測も簡単。

| Rebuildの場所 | できてしまうこと |
|---|---|
| プロフィール画像の更新 | 他人の画像を書き換える |
| ユーザー情報の取得 | 他人の情報を見る |
| メモ一覧（`findAll()`） | **全ユーザーのメモがまとめて返る** |
| フォルダ削除 | 他人のフォルダを削除する |

> **本来の形**：「このデータの持ち主は、今ログインしている人か」を毎回確認する。
> ```java
> if (!material.getUserId().equals(ログイン中のユーザーのID)) {
>     return 403;  // 禁止
> }
> ```

**認証（誰か）と認可（してよいか）は別物。** 認証を入れても、認可を書き忘れれば同じ穴が残る。

## 3. 入力を信用しない

### ✅ SQLインジェクション対策
```java
userRepository.findByUsername(request.getUsername());   // 安全
```
```java
// やってはいけない例：文字列をつなげてSQLを作る
"SELECT * FROM users WHERE username = '" + username + "'"
```
ユーザー名に `' OR '1'='1` などを入れられると SQL の意味が書き換わる。JPA のメソッドは**入力をデータとして扱い、SQLの一部として解釈しない**ので安全。

### ⚠️ Entity をそのまま受け取っている（マスアサインメント）
```java
@PostMapping
public Folder createFolder(@RequestBody Folder folder) {
    return folderRepository.save(folder);
}
```
送る側が好きな項目を入れられる：
- `userId` を他人にすれば、**他人名義でフォルダを作れる**
- `id` に既存IDを入れると `save()` は**上書き**として動き、他人のフォルダを書き換えられる可能性がある

> **本来の形**：**受け取ってよい項目だけを持つ専用クラス（DTO）**で受け取る。`userId` はログイン情報から決める。
> Rebuild でもログイン・登録は `LoginRequest`・`RegisterRequest` という DTO を使えている。

### ⚠️ アップロードファイルの種類を確認していない
```java
extension = originalName.substring(dotIndex);   // 送られてきた拡張子をそのまま使う
```
`.html` や `.svg` も保存でき、`/uploads/**` で公開されるので、悪意あるスクリプト入りのファイルを置かれる（**XSS** の足場）。

良いところ：
- ✅ 保存名を **UUID** にしている → `../../` で別の場所に書き込む攻撃や上書きを防げる
- ✅ **ファイルサイズを 5MB に制限**している

> **本来の形**：許可する拡張子を `.png`・`.jpg` などに限定（**許可リスト方式**）。可能なら中身が本当に画像かも確認する。

## 4. 情報を出しすぎない

### ✅ パスワードを返さない
```java
@JsonIgnore
private String password;
```
User をレスポンスで返しても、パスワード（ハッシュ）は JSON に含まれない。
ただし「Entity をそのまま返す」方式なので、**将来項目（メールアドレスなど）を追加すると自動で外に出る** → 返す項目を明示した DTO で返す方が安全。

### ⚠️ 内部エラーメッセージを返している
```java
.body("画像の保存に失敗しました: " + e.getMessage());
```
`e.getMessage()` にはサーバー内のフォルダの場所など**内部情報**が含まれることがある。

> **本来の形**：利用者には「保存に失敗しました」だけを返し、詳細はサーバーのログにだけ残す。

---

## 5. 秘密情報をコードに書かない

### ⚠️ 招待コードがソースコードに直書き（Rebuild）
- リポジトリが公開されていれば、**GitHub でコードを読めば誰でも分かる**
- 一度コミットした値は、後で消しても**Git の履歴に残り続ける** → 公開済みなら**値そのものを変える**必要がある

> **本来の形**：パスワード・APIキー・招待コードなどは、**環境変数や `.env`（Git に含めない）**から読み込む。Spring では `application.properties` の `${...}` で参照できる。

## 6. ブラウザとの約束（CORS）

**CORS は「どのWebサイトから、このAPIを呼んでよいか」をブラウザに伝える仕組み。**

```java
@CrossOrigin(origins = { "http://localhost:5173", "https://自分のドメイン" })  // ✅ 限定
@CrossOrigin                                                              // ⚠️ どこからでもOK
```

Rebuild では、限定しているControllerと、引数なし（全許可）のControllerが混在している。

**注意**：CORS は**ブラウザが守るルール**なので、curl などからのリクエストは止められない。**CORS は認証・認可の代わりにならない。**

## まとめ

| テーマ | 問い | Rebuildの状態 |
|---|---|---|
| 1. 認証 | あなたは誰？ | ✅ ハッシュ化 ⚠️ ログイン状態を保てない |
| 2. 認可 | それをしてよい？ | ⚠️ 持ち主の確認がほぼない（**最重要**） |
| 3. 入力の検証 | 送られてきたものは安全？ | ✅ SQLインジェクション対策 ⚠️ Entity直受け、ファイル種別 |
| 4. 情報の出しすぎ | 余計なことを返していない？ | ✅ パスワードを返さない ⚠️ 内部エラーの露出 |
| 5. 秘密情報 | コードに鍵を書いていない？ | ⚠️ 招待コードの直書き |
| 6. CORS | どのサイトから呼べる？ | ✅ 一部限定 ⚠️ 設定が不統一 |

- 学ぶ順番は **1・2（認証・認可）が最優先**。ここが整うと他の問題も直しやすくなる
- この6つは Web セキュリティの代表的なチェックリスト **OWASP Top 10** の主要項目に対応している
- Fizzy を読むときは「**認証と認可がどこで行われているか**」を探すと学びが大きい
